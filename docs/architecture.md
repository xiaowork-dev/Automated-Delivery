# 业务设计与事务边界

浏览器通过 Nginx 访问 Vue 页面，`/api/v1` 由 Nginx 转发给 Spring Boot。JWT 认证后，Controller 只接收和验证参数，Service 执行业务，MyBatis-Plus Mapper 读写 MySQL。数据库迁移通过 Flyway 运行。

## 库存和金额

可用库存始终来自 `redeem_code` 中状态为 `UNUSED` 且未过期的数量。商品列表展示可能来自短时缓存，创建订单及支付必须查询数据库。Redis 不能决定兑换码归属，失效或宕机不应破坏订单与库存一致性。

金额使用 `BigDecimal`，数据库使用 `DECIMAL(10,2)`。创建订单保存商品名和单价快照，后续改价或改名不影响订单。

## 模拟支付

1. 开始事务，锁定订单行，验证访问者身份。
2. 已发货或已完成的订单返回当前结果，不新增卡密、不重复扣库存。
3. 校验订单仍为 `WAIT_PAY`、未超时。
4. 从该商品的可用兑换码中以 `SELECT ... FOR UPDATE` 取一条。
5. 带 `status = UNUSED` 条件绑定兑换码、用户和订单。
6. 订单更新为 `DELIVERED`，记录模拟支付和发货时间、交付记录。
7. 提交事务。任意异常将订单、兑换码和日志一起回滚。

支付事务采用 `READ_COMMITTED`，仍保留订单与卡密记录锁。真实 MySQL 回归发现 `REPEATABLE_READ` 下库存索引的间隙锁竞争会造成部分请求死锁回滚；改用 `READ_COMMITTED` 后，20 轮单库存五订单竞争都返回一单成功、其余明确缺货，并验证多库存竞争及同订单 20 次并发重试。

数据库 `redeem_code.code` 全局唯一、`redeem_code.order_id` 唯一。库存为空时保持订单待支付并返回 `409 OUT_OF_STOCK`，不会留下已支付但未发货的半完成状态。

## 自助兑换

事务中锁定兑换码，验证绑定用户、状态和有效期，将 `ASSIGNED` 原子更新为 `USED`，记录成功兑换，并将订单更新为 `COMPLETED`。成功兑换记录的唯一约束防止重复有效兑换。再次提交返回 `409 CODE_ALREADY_USED`。

## 权限和日志

用户只能访问自己的订单及兑换码。管理员路由必须通过后端角色验证。用户被禁用后，其旧令牌也不能继续访问。管理台库存页默认展示脱敏卡密；完整卡密只出现在有权限的订单详情。

下架商品、作废卡密、关闭待支付订单和更改用户状态写审计记录。业务日志只记录订单号、用户 ID、商品 ID、卡密 ID 和请求 ID；不记录密码、JWT 或完整卡密。

## 超时和恢复

定时任务仅更新过期的待支付订单及尚未兑换的过期卡密，状态条件保证重复执行安全。支付与任务竞争由数据库行锁和状态条件协调。MySQL 使用持久化卷；升级前备份，数据库结构按迁移版本演进。

## 验证依据

行锁语义依据 [MySQL 8.0 Locking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。核心结论以本项目测试为准：H2 用于快速服务测试，真实 MySQL 用于 HTTP 交易和并发验收，两类测试分别记录，不相互替代。
