# 后端运行与一致性说明

要求 Java 21、Maven 3.9、MySQL 8。复制项目根目录的 `.env.example` 并按部署指南配置，或为本地启动设置对应环境变量。后端不会读取 `.env`；Compose / 启动脚本负责注入环境变量。

```sh
mvn verify
java -jar target/automated-delivery-1.0.0.jar
```

数据库通过 Flyway `V1__initial_schema.sql` 创建。不得手工改已发布的迁移；未来结构更新使用下一编号 migration。数据库约束包括唯一用户名、订单号、兑换码、订单卡密绑定、成功兑换记录与发货日志。金额均为 `BigDecimal` / `DECIMAL(10,2)`。

必填 `JWT_SECRET` 至少 32 字节。`ADMIN_USERNAME` / `ADMIN_PASSWORD` 只在不存在该管理员时创建管理员，后续启动不会覆盖密码。未提供管理员密码时不会创建默认口令账号。`APP_SEED_DEMO=true` 只在空商品库生成三个演示商品及随机兑换码。密码至少 8 字符且 UTF-8 编码不超过 72 字节。修改密码后旧令牌立即失效；禁用账号后现有令牌立即失效。

API 契约见项目 `docs/implementation-plan.md`。公开商品仅查询上架商品。返回时间均包含 `+08:00`；导入有效期接受本地时间或 ISO 8601 偏移时间并转换到北京时间。卡密导入格式为 4–128 位字母、数字、下划线或连字符，每次最多 10000 行；空行忽略、重复与无效分别计数。后台列表只返回掩码，完整码仅在经过归属检查的订单详情中返回。

HTTP 请求经过 Spring Security 的 JWT 验证与数据库账号状态检查，控制器验证 DTO，再调用 Service。业务事务集中在 Service：下单事务写订单和名称/金额快照；支付事务始终先锁订单，再锁一条未过期 `UNUSED` 库存，通过状态条件更新绑定码、更新订单、写唯一发货日志。任一步异常会回滚，未抢到库存的订单保持 `WAIT_PAY`。成功后的重复支付直接返回已绑定的同一码，不再扣库存。`Idempotency-Key` 并非必要条件，幂等由数据库状态、行锁与唯一约束共同实现。

兑换、已分配卡密作废也遵守订单→卡密锁顺序。兑换仅允许绑定买家把 `ASSIGNED` 改为 `USED`，与唯一成功记录、订单 `COMPLETED` 一起提交。再次兑换返回 `CODE_ALREADY_USED`。管理员无法兑换别人的码，后台查看权限与买家归属权限分别受控。

每分钟超时任务通过带状态条件的 SQL 关闭待支付订单、处理过期卡密；重复执行安全。它不会关闭已发货订单。用户取消和管理员关闭只处理 `WAIT_PAY`。

`REDIS_ENABLED=true` 时商品详情缓存 30 秒，商品维护、导入、支付、作废在数据库提交后清缓存；列表与交易判断使用数据库。过期任务后详情展示最多可能延迟 30 秒，实际库存判断不会受此影响。Redis 以原子 Lua 脚本实施注册 10 次/分钟、登录 30 次/分钟、兑换每用户 20 次/分钟限流。Redis 故障时缓存和限流降级，事务与库存仍由 MySQL 保证。部署在代理后应在受信代理处配置客户端 IP；不要直接相信任意客户端的转发头。

自动测试使用 H2 MySQL 模式验证事务回滚、锁竞争、幂等、归属、快照、过期、鉴权与 Redis 故障降级；H2 不代替 MySQL 验收。根目录 `scripts/api-acceptance.py` 对真实启动的 MySQL 后端执行完整 HTTP 闭环与并发验证。健康接口 `/actuator/health` 为部署检查公开，仅输出状态。

支付事务显式采用 `READ_COMMITTED`。订单唯一键定位和库存行仍使用 `FOR UPDATE`；库存检索避免默认 `REPEATABLE_READ` 范围扫描产生的间隙锁竞争，使未抢到库存的并发请求返回确定的 `OUT_OF_STOCK`。数据库行锁、条件更新、唯一约束和整体回滚仍负责一致性。[MySQL 官方事务隔离说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html)解释了记录锁、间隙锁及非匹配行锁释放行为。

真实 MySQL 驱动回归测试 `MySqlConcurrencyTest` 默认跳过，需设置 `TEST_MYSQL_URL` 指向**独立测试库**，以及 `TEST_MYSQL_USER` / `TEST_MYSQL_PASSWORD` 后运行 `mvn verify`。测试写入唯一命名的商品、订单与测试用户，不删除数据。它执行 20 轮“库存 1、并发 5 单”、库存 10 并发 20 单及同单 20 次并发支付，并断言结果、订单状态、库存绑定、发货日志一致。回滚测试在此独立库创建临时触发器，故意让发货日志插入失败，验证此前卡密分配与订单变更全部回滚，再移除触发器验证重试成功；测试账号因此需要 `TRIGGER` 权限，禁止指向生产库。H2 与 Redis 测试一同执行；在 CI 应启用这套真实 MySQL 回归。
